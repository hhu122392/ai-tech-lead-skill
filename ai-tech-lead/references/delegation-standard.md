# 派工标准

## 1. 派工不是“把需求转发出去”

错误：

```text
登录有问题，你修一下。
```

正确：主 Agent 先确认当前行为、目标行为、调用链、接口约束和测试方式，再下发一个可独立验收的工程结果。

> 不派“问题”，只派“合同”。

## 2. 五可门槛

每个任务必须同时满足：

### 可定义

- 只有一个主要结果
- 当前行为与目标行为清楚
- 非目标和不变量清楚
- 没有未决的关键架构选择

### 可隔离

- 明确模块、文件或符号
- 明确允许和禁止写入范围
- 与其他任务依赖关系明确
- 同一文件没有并行写入者

### 可验证

- 有可执行命令或可观察证据
- 验收标准不是“看起来不错”
- 主 Agent 能独立重现和判断
- 测试失败能定位到合同目标

### 可回滚

- 有基线 commit／分支／worktree
- 不直接对生产数据做不可逆操作
- 必要时有备份、dry-run 或迁移回滚
- 子 Agent 无权自行发布到生产

### 可追责

- 有任务编号和唯一负责人
- 有交付格式、状态和证据
- 有停止上报条件
- 能知道哪些变更来自哪个任务

任意一项失败：继续调查、拆分或由主 Agent 保留。

## 2.1 基线与工作区安全

- Git 项目必须记录基线 commit、分支、工作区状态和用户已有 diff；非 Git 项目必须先创建完整文件快照和恢复路径，否则不得派写任务。
- 共享工作区写入前必须完成预检：记录用户改动、锁定写入范围，并在交付时比较任务前后 diff。无法自动区分用户改动时，停止派工。
- 默认使用独立 worktree 或等价隔离目录。Test Engineer 不得覆盖 Implementer 已拥有的测试文件，除非合同明确转移所有权。
- 文件所有权、任务状态和审批记录必须有唯一任务 ID；不能只依赖聊天中的口头约定。
- 通过终端、插件或其他接口调用外部 Agent 前，必须完成 `references/external-agent-preflight.md`：证明实际生效的 YOLO／免确认等价权限和当前模型最高／实际 thinking。任一证据缺失就标记 `BLOCKED`，不得用反复点击 `allow` 代替。

## 3. 任务粒度

一个执行任务应满足：

- 一个可命名的工程结果
- 一个主要模块或明确的文件集合
- 一套独立可运行的验收方法
- 不需要执行者重新设计全局架构
- 失败后不影响其他任务继续判断

出现下列信号时继续拆分：

- Prompt 中同时出现多个“并且”且能独立验收
- 需要修改互不相关的模块
- 执行者必须先决定 API、数据模型或权限策略
- 测试命令覆盖多个不相关目标
- 预计多个 Agent 会修改同一核心文件

## 4. 任务依赖图

建议顺序：

```text
事实调查
  ↓
接口／数据契约
  ↓
实现任务（可并行的互斥文件范围）
  ↓
独立测试
  ↓
只读审查
  ↓
主 Agent 集成与回归
```

不要在接口尚未固定时并行派前后端实现。

## 5. 两阶段派工

R0／简单 R1 可一次性实现。

R2／R3 必须分两阶段：

1. **理解与计划阶段（只读）**：复述目标、列出调用链、计划修改文件、风险和测试。
2. **实现阶段**：主 Agent 审批计划并补齐合同后，才允许写代码。

## 6. 文件所有权

- 同一文件同一时间只有一个写入负责人。
- 只读 Agent 可以并行读取同一文件。
- 若两个任务必须写同一文件：串行执行、拆分接口，或使用独立 worktree 后由主 Agent 语义合并。
- 子 Agent 不得提交、合并、推送或发布，除非合同明确授权。

## 6.1 任务生命周期

任务至少使用以下状态：`PENDING`、`RUNNING`、`DONE`、`PARTIAL`、`BLOCKED`、`REJECTED`、`INTEGRATED`、`CANCELLED`、`TIMED_OUT`。

- 每次尝试记录 Agent、模型、开始／结束时间、工作区和结果证据。
- 超时、崩溃或中断后先检查半成品 diff，再决定恢复、回滚或重新派工；不得直接复用未知状态的工作区。
- 重试必须增加尝试编号并说明改变了什么；同一合同不得无限重试。

## 7. 何时不要派工

- 修改极小，派工成本高于实现成本
- 结果依赖主 Agent 当前大量隐性上下文且无法可靠压缩
- 验收无法客观执行
- 涉及不可逆生产操作
- 涉及尚未决策的安全／权限／账务架构
- 工作区已有复杂未提交改动，无法安全隔离

此时主 Agent 直接处理，或先创造可派工条件。
