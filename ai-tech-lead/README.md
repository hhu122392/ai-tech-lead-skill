# AI Tech Lead Skill（技术总监模式）

## 🎯 简介

让主 Agent 当技术总监：把编码执行交给更便宜的执行 Agent（原生子 Agent，或终端里的 PI / Claude Code），自己保留判断、验收和责任。

适合多文件功能、Bug 修复、重构、迁移、集成这类"做完要有人签字"的活。不适合改一行代码或者纯咨询。

---

## 🧠 核心理念

**可以下放编码，不能下放判断。**

下面这些事永远留在主 Agent 手里：需求理解、架构决策、验收标准、任务拆分和写入边界、最终 Diff 审查、集成后独立验证、对用户的完成结论。

子 Agent 对执行报告负责；主 Agent 对最终正确性负责。

---

## 🚦 九步工作流

1. **建立事实与基线**（读规则、看真实调用链、确认工作区脏不脏、基线是否通过）
2. **定义完成标准**（Given／When／Then + 验证方式）
3. **风险分级**（R0～R3，风险越高主 Agent 留的设计越多）
4. **判断能否派工**（五可：可定义、可隔离、可验证、可回滚、可追责）
5. **生成任务合同**（写清允许改什么、禁止改什么、怎么验收、什么时候停下上报）
6. **派工与监督**（一任务一窗口，最多三个写窗口）
7. **检查交付实物**（不看总结，看仓库和 Diff）
8. **独立测试与代码审查**（主 Agent 自己重跑必要的命令）
9. **集成与签字**（验收矩阵逐条对应，结论只能是 VERIFIED COMPLETE / IMPLEMENTED, NOT FULLY VERIFIED / BLOCKED）

---

## 🔒 不可违背的门槛

- 没有验收标准不派工；不把"问题"直接丢出去，只下发定义清楚的工程任务。
- 同一文件同一时间只能有一个写入负责人。
- 子 Agent 说"测试通过"不算证据；主 Agent 没看 Diff、没自己跑验证，不许说完成。
- 不许为了过测试削弱断言、删测试、吞异常或扩大权限。
- 外部 Agent 的能力一律先跑 `--help` 取证，凭记忆断言"做不到"算违规。

---

## 🖥️ 终端派活（PI / Claude Code）

- **可视化**：一律开可见终端窗口，一任务一窗口，标题写任务号，用户能实时看到使用情况。
- **留痕**：窗口和主 Agent 之间没有管道，启动命令必须同时把输出写进日志文件；窗口关闭后，日志就是唯一证据。
- **关窗**：进程退出拿到退出码 **且** 主 Agent 验收完成，两个条件都满足才关。
- **窗口被人手动关了**：不许当成成功或失败，标记 `TIMED_OUT`／`CANCELLED`，去查半成品 Diff。

调用前还有两道硬检查：权限／YOLO 是否真的生效、thinking 是否达到最高可用挡位。两者的取证要求见 `references/external-agent-preflight.md`。

---

## 🔁 经验沉淀（Memory）

**跑一次，长一智。**

每次真实任务的收尾都要把这次踩的坑写进 `MEMORY.md`：一节一条，写清场景、原以为、实际是、证据、代价、改了什么规则。

- 能改规则的就当场改进 `SKILL.md` 或 `references/`，条目标成 `已入规`。
- 还没定论的标 `待入规`，不装作已经解决。
- 新结论推翻旧结论时改旧条目，不许两条矛盾结论并存。

跑任务 → 沉淀 → 改规则 → 再跑。这是这套 Skill 唯一的迭代方式，不靠感觉优化，靠踩过的坑。

## 📁 文件结构

```
SKILL.md                    主标准：使命、门槛、九步工作流、完成检查
MEMORY.md                   经验沉淀：真实任务踩过的坑和验证过的做法
README.md                   本文件
references/                 细则：前置检查、任务合同、测试与验收、代码审查、风险分级等
assets/                     模板：验收矩阵、任务合同、派工计划、交付报告、最终签字
examples/                   范例：功能拆解、任务合同样例
agents/openai.yaml          角色配置
```

---

## 🛠️ 怎么用

```text
$ai-tech-lead 帮我把 XXX 功能做完，要能过 CI 的 typecheck 和单测
```

给它的输入越具体越好：目标行为、不能破坏的东西、验收方式。它会把剩下的设计、拆分、派工和监督接过去，最后给你一份带证据的交付说明。
